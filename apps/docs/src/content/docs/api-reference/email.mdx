title: Email API
description: Read and send email, manage addresses, inspect usage, and configure signed webhooks.

Email endpoints require an API key scoped to the identity, or a signed-in session or wallet
request signature of the account that owns it. See
[authentication](/api-reference/overview/#authentication).

## Inbox and retention

```http
GET    /api/v1/agents/:id/email
PATCH  /api/v1/agents/:id/email/:messageId
DELETE /api/v1/agents/:id/email/:messageId
```

Use `limit`, `unreadOnly` and `direction` (`inbound` or `outbound`) on list requests. Accepted
message content is kept for 15 days on the Free plan and 30 days on paid plans; `limits.retentionDays`
reports the current value, and a plan change applies to the messages already kept. `PATCH` with
`{ "read": true }` or `{ "read": false }` marks a message. Deleting a message makes it unavailable
immediately.
Each message has a `status`. Sent mail is `queued`, `scheduled` (with `sendAt`), `sending`, `sent`,
`partially_sent`, `failed`, `suppressed` or `cancelled`; received mail is `stored`.
The response can also include `addressChange` and `mailStatus`. `sync=false` skips the current
provider check and may return `mailStatus.state: "unchecked"`; this is not a readiness confirmation.
`addressChange: { "phase": "unavailable" }` means the change status could not be checked. Other
inbox data can still be read, but do not infer that no request is pending or that it completed.

## Primary address and aliases

```http
PATCH  /api/v1/agents/:id/email
POST   /api/v1/agents/:id/email/aliases
DELETE /api/v1/agents/:id/email/aliases?emailAddress=billing@example.com
```

Changing the primary username requires `confirmReplace: true`. After completion, the previous
primary address stops accepting new mail; existing messages remain available until deleted or expired.

Depending on the inbox, these operations return either the existing completed result or
HTTP `202` with a `change` object containing `requestId`, `action`, `target`, and `phase`. An already-completed asynchronous
request returns the same `change` shape with HTTP `200` and phase `completed`. Alias creation can
still return its immediate completed result with HTTP `201`.

For asynchronous changes, send a UUID `Idempotency-Key` and preserve it with the operation.
Retry an unconfirmed request only explicitly, with the identical UUID and target. Inspect
`GET /api/v1/agents/:id/email` for `addressChange`; do not start another address mutation while the
previous one is unresolved. `pending`, `fenced`, `applying`, `native_applied`, and `projected` are
not completion. `uncertain` and `rejected` require review; `cancelled` is not a successful change.
Only `completed` confirms the new routing. Readiness is reported separately by `mailStatus`.

## Send mail

```http
POST /api/v1/agents/:id/email/send
```

```json
{
  "to": ["operator@example.com"],
  "cc": "lead@example.com",
  "fromAddress": "billing@example.com",
  "subject": "Service online",
  "text": "The identity is ready.",
  "html": "<p>The identity is <b>ready</b>.</p>",
  "attachments": [{ "filename": "status.pdf", "content": "JVBERi0xLjcK..." }],
  "sendAt": "2026-12-01T09:00:00Z"
}
```

| Field          | Required | Notes                                                                                                                                                     |
| -------------- | -------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `to`           | Yes      | One address or a list. `to`, `cc` and `bcc` together are at most 50.                                                                                      |
| `cc`, `bcc`    | No       | `bcc` recipients get the message, but no header in it names them.                                                                                         |
| `replyTo`      | No       | One address or a list.                                                                                                                                    |
| `fromAddress`  | No       | The primary address or an active alias. The primary when left out.                                                                                        |
| `fromName`     | No       | The sender name, one line of up to 100 characters. The profile name when left out.                                                                        |
| `subject`      | Yes      | One line of up to 998 characters.                                                                                                                         |
| `text`, `html` | One      | At least one of the two; each at most 2 MB.                                                                                                               |
| `attachments`  | No       | Up to 20 files, 10 MB together: `filename`, base64 `content`, optional `contentType`. Programs and scripts (such as `.exe`, `.js` or `.bat`) are refused. |
| `sendAt`       | No       | Send later, up to 30 days ahead. A past time sends now.                                                                                                   |

Every message is signed with the domain's own DKIM keys, RSA and Ed25519, so it passes DKIM and
DMARC alignment at the receiving server. It is stored sealed (encrypted at rest) for the plan's
retention and delivered to each recipient separately. A delivery that a receiving server defers
is retried for up to 72 hours; one it refuses is not retried. An address that refused mail as
unknown is added to the domain's suppression list, and later messages skip it.

A request with an unknown field is refused with `400 INVALID_REQUEST`, naming the field. A
message that fails a check is refused with `422` and a stable code, such as `INVALID_RECIPIENT`,
`TOO_MANY_RECIPIENTS`, `BODY_REQUIRED`, `FROM_ADDRESS_NOT_ALLOWED`, `ATTACHMENT_TYPE_BLOCKED`,
`ATTACHMENTS_TOO_LARGE` or `SEND_AT_TOO_FAR`, with `details.field` naming the field. A refused
message uses none of the allowance.

The answer has the message `id`, its `messageId` header, `status` (`queued`, or `scheduled` with
`sendAt`), one entry per recipient in `messages`, and `usage` (`limit`, `used`, `remaining`).
When some recipients are on the suppression list, the message is queued for the others with
`202 EMAIL_PARTIALLY_QUEUED`, and those recipients show `status: "suppressed"`. When every
recipient is, nothing is sent: `422 EMAIL_RECIPIENTS_SUPPRESSED`. Deleting a message that is
scheduled or still being retried stops it for every recipient it has not reached.

Every recipient counts once against the combined monthly sent and received allowance, and only
recipients the message is queued for are counted. A send that would go past the allowance is
refused with `429 EMAIL_QUOTA_EXCEEDED`; `details` gives `remaining`, `requested` and `resetsOn`.

Send `Idempotency-Key` when a client may retry. Within 24 hours the same key and the same request
return the first answer (with the header `Idempotent-Replayed: true`) instead of sending again.
The key is bound to the normalized request: the same key with different content returns
`409 IDEMPOTENCY_KEY_REUSED`, and a retry while the first request is still being handled returns
`409 IDEMPOTENCY_KEY_IN_PROGRESS`. A request that failed gives its key back, so it can be retried
with the same key.

Each identity can make 12 send or batch requests a second. More return
`429 EMAIL_RATE_LIMITED` with `Retry-After`.

## Batch send

```http
POST /api/v1/agents/:id/email/batch
```

```json
{
  "validationMode": "partial",
  "messages": [
    { "to": "ops@example.com", "subject": "Status", "text": "Online." },
    { "to": "lead@example.com", "subject": "Status", "text": "Online." }
  ]
}
```

A batch carries 1 to 100 messages, each with the same fields as a single send, in one request of
at most 20 MB. Every message is checked before any is queued. `validationMode: "strict"` (the
default) sends nothing when any message is invalid: `422 BATCH_INVALID`, with `details.errors`
listing each invalid message by `index`, `code`, `message` and `field`. `"partial"` queues the
valid messages and lists the others in `errors`.

The answer is `202` with `status`, `jobs` (one per queued message, with its `index` in the
request and its per-recipient `messages`), `errors` and `usage`. When some messages or recipients
were not queued it also has `code: "BATCH_PARTIALLY_QUEUED"` and a `message`. Batches follow the
same allowance, suppression and idempotency rules as single sends; treat the per-recipient
results as the source of truth.

## Usage

```http
GET /api/v1/agents/:id/email/usage
```

The response reports the current plan, monthly limit, sent, received, reserved, used, remaining,
`requestsPerSecond` and the cycle dates (the calendar month, UTC). Check it before large sends,
but still handle concurrent `429` responses.

## Signed inbound webhook

```http
GET   /api/v1/agents/:id/email/webhook
PUT   /api/v1/agents/:id/email/webhook
PATCH /api/v1/agents/:id/email/webhook
```

`PUT` configures an HTTPS endpoint and can return its signing value once. `PATCH` rotates that
value. Store it in the receiving application's secret store and verify the event identifier,
timestamp, and HMAC-SHA256 signature before accepting a delivery.

`metadata` payloads contain message metadata and an authenticated content URL. `inline_text` can
include plain text up to 256 KiB. Webhook delivery status and supported replay actions are exposed
through the identity's webhook endpoints.

## Blocklist

```http
GET    /api/v1/agents/:id/email/blocklist
POST   /api/v1/agents/:id/email/blocklist
DELETE /api/v1/agents/:id/email/blocklist/:blockId
```

Entries can match one normalized email address or an entire domain and apply to inbound senders and
outbound recipients.

## Successful responses

| Operation                   | Success | Required outer fields                                               |
| --------------------------- | ------- | ------------------------------------------------------------------- |
| Inbox GET                   | `200`   | `inbox`, `addresses`, `limits`, `messages`                          |
| Message PATCH               | `200`   | `message`                                                           |
| Message DELETE              | `200`   | `deleted`, `messageId`                                              |
| Primary address PATCH       | `200`   | `inbox`, `addresses`, `message`                                     |
| Alias POST                  | `201`   | `address`, `addresses`                                              |
| Alias DELETE                | `200`   | `deleted`, `addresses`                                              |
| Send POST, normal enqueue   | `201`   | `id`, `status`, `messageId`, `sendAt`, `messages`, `usage`          |
| Send POST, partial enqueue  | `202`   | `id`, `status`, `code`, `message`, `messages`, `usage`              |
| Batch POST, normal enqueue  | `202`   | `status`, `jobs`, `errors`, `usage`                                 |
| Batch POST, partial enqueue | `202`   | `status`, `code`, `message`, `jobs`, `errors`, `usage`              |
| Usage GET                   | `200`   | Plan/cycle/counter fields, `used`, `remaining`, `requestsPerSecond` |
| Webhook GET                 | `200`   | `webhook`, which can be `null`                                      |
| Webhook PUT, update         | `200`   | `webhook`                                                           |
| Webhook PUT, creation       | `201`   | `webhook`, `signingSecret`                                          |
| Webhook PATCH, rotation     | `200`   | `webhook`, `signingSecret`                                          |
| Blocklist GET               | `200`   | `entries`                                                           |
| Blocklist POST              | `201`   | `entry`                                                             |
| Blocklist DELETE            | `200`   | `ok`                                                                |

`EMAIL_PARTIALLY_QUEUED` and `BATCH_PARTIALLY_QUEUED` identify accepted subsets.
Queued is not delivered: a message's `status` in the inbox list moves on to `sent`,
`partially_sent` or `failed` as its deliveries finish.

Do not resend the entire request with a new idempotency key after partial or
uncertain acceptance. Keep the original key and reconcile its returned items.
The `signingSecret` from webhook creation or rotation is sensitive: retain it
only in the receiving application's protected storage, never model context,
public source, analytics or logs. It is not returned again on an ordinary update.
